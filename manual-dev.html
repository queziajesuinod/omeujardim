03

Identificador: UUIDv7, e não TSID

Você perguntou TSID ou UUID. A resposta é UUIDv7, e vale entender por que, porque o motivo decide também como a sincronização funciona.

OpçãoTamanhoOrdenávelO problema
UUIDv416 bytesnãoInserção aleatória no índice B-tree causa divisão de página, índice inchado e cache frio. É o clássico "por que meu insert ficou lento com 10 milhões de linhas".
TSID8 bytessimCabe em bigint e é ótimo, mas precisa de um id de nó coordenado entre quem gera. Com o celular gerando id offline, cada aparelho vira um nó, e você teria que distribuir e controlar esses números.
UUIDv716 bytessimNenhum relevante aqui. Padrão publicado na RFC 9562, tipo uuid nativo no Postgres, e os 48 bits iniciais são o timestamp em milissegundos.

Os 8 bytes a mais do UUIDv7 sobre o TSID custam cerca de 160 MB a cada 10 milhões de linhas com quatro índices. Para este app, é irrelevante. O que não é irrelevante é o celular poder criar um id sozinho, sem pedir nada ao servidor e sem coordenar com ninguém.

O que isso destrava

Como o id nasce no aparelho, subir o mesmo registro duas vezes não cria dois. A sincronização fica idempotente sem uma linha de lógica de conflito, que é justamente onde app offline costuma morrer.

// api/src/db/models/registro.js
Registro.regar = async function ({ id, usuarioId, praticaId, dataRef }, t) {
  // id veio do celular. Mandar duas vezes não cria dois.
  const [registro] = await Registro.findOrCreate({
    where: { id },
    defaults: { id, usuarioId, praticaId, dataRef },
    transaction: t,
  });
  return registro;
};
Regra

O servidor aceita o id do cliente, mas nunca confia nele sem validar: precisa ser UUID versão 7. Um id vindo de fora é entrada de usuário como qualquer outra.

04

Banco e migrações

Schema muda por migração, sempre. Não existe exceção, nem em desenvolvimento.

Convenções fixas
  • Tabela no singular e em snake_case: registro, pedido_oracao.
  • Coluna em snake_case no banco, camelCase no código. Resolvido uma vez em define.underscored.
  • Datas em português: criado_em, atualizado_em, removido_em.
  • Migração nomeada pelo que faz: 20260903120000-cria-usuario.js.
  • Toda migração tem down que realmente desfaz, inclusive apagando o tipo ENUM criado.
Proibido
  • sequelize.sync() em qualquer ambiente. Ele mente sobre o estado do schema.
  • Editar migração já aplicada em produção. Crie outra.
  • Índice sem nome. Sem nome, você não consegue removê-lo depois.
  • Chave estrangeira sem onDelete explícito.
  • Coluna TEXT sem limite recebendo entrada de usuário.

registro (usuario_id, data_ref)A tela Hoje e o calendário de constância, que são as consultas mais quentes.

O dia devocional começa às 4h

Este é o detalhe que quebra app de hábito e ninguém percebe na revisão. Quem ora às 23h50 e quem ora às 00h10 não podem cair em dias diferentes. Por isso data_ref é DATEONLY, calculado no cliente a partir do fuso da pessoa e do início do dia dela, e concluido_em é o carimbo real com fuso, usado só para conquista de horário.

// app/lib/id.ts
export function diaDevocional(agora = new Date(), inicioHora = 4): string {
  const d = new Date(agora);
  if (d.getHours() < inicioHora) d.setDate(d.getDate() - 1);
  return `${d.getFullYear()}-${mm(d)}-${dd(d)}`;
}
05

Segurança e LGPD

Existe um fato jurídico que molda a arquitetura inteira, e é melhor encarar ele agora do que na véspera de publicar.

O fato

A LGPD, no artigo 5º, inciso II, define convicção religiosa como dado pessoal sensível. Este app não trata dado sensível por acidente em algum campo: ele é feito inteiro de dado sensível. O que a pessoa escreve no devocional, por quem ela ora, quanto ela jejua.

Consequência prática imediata: dado sensível não aceita legítimo interesse como base legal. O artigo 11 exige consentimento específico e destacado, para finalidades específicas.

O que isso vira em código

ExigênciaImplementação
Consentimento específico e destacadoDuas caixas separadas no cadastro, nenhuma marcada por padrão, e a API recusa cadastro sem as duas: aceitaTermos e aceitaDadosSensiveis.
Provar a que a pessoa consentiuColunas consentimento_versao e consentimento_em. Texto mudou, versão sobe, consentimento é pedido de novo.
Revogar tão fácil quanto consentir (art. 8º, §5º)Botão em Ajustes, não e-mail para o suporte.
Acesso e portabilidade (art. 18)GET /v1/meus-dados devolve tudo em JSON legível, com o diário já decifrado.
Eliminação (art. 18, VI)Exclusão lógica na hora, expurgo real em 30 dias. paranoid: true sozinho não atende a lei.
Comunicação de incidente (art. 48)A Resolução CD/ANPD nº 15/2024 fixou 3 dias úteis a partir do conhecimento. Tenha o plano escrito antes de precisar.

Cifra do diário, e o preço dela

O texto do devocional e a lista de oração vão cifrados no banco com AES-256-GCM, que cifra e autentica ao mesmo tempo. O truque de implementação é fazer isso num campo virtual do model, para que a decisão saia das mãos de quem escreve a rota com pressa seis meses depois.

// api/src/db/models/anotacao.js
texto: {
  type: DataTypes.VIRTUAL,
  get() { const g = this.getDataValue('textoCifrado'); return g ? decifrar(g) : null; },
  set(valor) { this.setDataValue('textoCifrado', cifrar(valor)); },
},
O preço, dito na cara

Com o texto cifrado, o Postgres não consegue buscar dentro dele. Não existe truque: ou o servidor lê, ou ele busca. Escolhemos que ele não lê.

A busca do diário roda no celular, contra a cópia local em SQLite com FTS5, que o app já tem por ser offline primeiro. O servidor guarda e devolve, não pesquisa. Isso também significa que a busca só enxerga o que já sincronizou naquele aparelho, e isso precisa aparecer na interface.

Autenticação

Acesso em JWT de 15 minutos, refresh de 30 dias guardado no banco como hash, nunca como token. Se o banco vazar, ninguém se passa por ninguém.

O refresh é rotativo e agrupado em família. Quando o servidor vê um refresh já consumido, ele derruba a família inteira e obriga todo mundo a entrar de novo. É a forma mais simples de detectar roubo de token sem hardware especial: se alguém roubou e usou, o dono legítimo também vai tentar usar, e a colisão denuncia.

Senha

Argon2id nos parâmetros da OWASP, 19 MiB e 2 iterações, com rehash automático quando você subir o custo. Mínimo de 10 caracteres, sem exigir zoológico de símbolos.

No aparelho

Token em expo-secure-store, que usa Keychain e Keystore. Nunca em AsyncStorage, que é arquivo comum e sai no backup.

No log

Redação obrigatória de authorization, senha, texto, titulo, pessoa e refresh. Log com diário dentro é vazamento com data marcada.

A falha que mais aparece em API, e o antídoto

Autorização por objeto. Não basta saber quem é a pessoa, é preciso verificar que o recurso pedido é dela. Sem esta linha existe IDOR, que é o item número um da lista da OWASP para APIs.

// api/src/rotas/registros.js
const pratica = await Pratica.findOne({ where: { id: dados.praticaId, usuarioId } });
if (!pratica) return reply.code(404).send({ erro: 'pratica_nao_encontrada' });
// 404, não 403: dizer "existe mas não é sua" já entrega informação.
Não faça, e é fácil fazer sem pensar

Mandar conteúdo de diário para ferramenta de analytics, mesmo que só o tamanho do texto. Usar o diário para treinar modelo sem consentimento separado para essa finalidade. Backup sem cifra, ou chave guardada junto do backup. E-mail da pessoa na URL, que vai parar em log de proxy. Notificação push mostrando a anotação na tela de bloqueio.

06

Offline primeiro

A pessoa registra oração às 5h da manhã, no ônibus, no culto, em lugar sem sinal. Se gravar depender de rede, o app falha exatamente no momento de uso.

  1. Gravar é local e imediato. A tela nunca espera a rede, nunca mostra roda antes de confirmar a rega.
  2. A operação entra numa fila de saída no SQLite, com o id já gerado.
  3. Quando há rede, a fila sobe em ordem. Subir duas vezes não duplica, porque o id é o mesmo.

O tratamento de erro da fila importa mais que o caminho feliz: falha de rede mantém o item, erro 4xx que não é 429 descarta. Repetir para sempre uma requisição inválida é como se cria fila zumbi que nunca esvazia.

if (resposta.ok || resposta.status === 409) { remover(item); continue; }  // 409 = já existe lá
if (resposta.status >= 400 && resposta.status < 500 && resposta.status !== 429) { remover(item); continue; }
throw new Error(`HTTP ${resposta.status}`);  // 5xx e rede: tenta de novo depois

Traduzindo tempo em mola

O design system fala em duração e curva de bézier, que é a linguagem do CSS. O Reanimated fala em mola, com amortecimento e rigidez. A tradução dos três tokens de tempo está no tema, calibrada para dar a mesma sensação: nada pisca, nada salta.

A regra que fecha

Toda animação passa por useMovimentoReduzido(), que lê AccessibilityInfo.isReduceMotionEnabled() e escuta a mudança. Quem pediu menos movimento no sistema recebe o estado final direto, sem transição. Isso não é enfeite de acessibilidade: para parte das pessoas, movimento na tela causa enjoo de verdade.

08

Muitos ao mesmo tempo

Este app tem um perfil de carga incomum e perigoso: quase todo mundo usa na mesma meia hora. Um app de tarefas espalha o uso pelo dia; um app devocional concentra tudo entre 5h30 e 7h.

A conta que dá o tamanho do problema

Com 100 mil contas e 60% ativas por dia, se 40% dessas usarem na janela de 30 minutos da manhã, são 24 mil sessões em 1800 segundos. A umas 5 requisições por sessão, dá 65 por segundo em média e talvez 200 no pico. Isso é pouco. Uma instância de 2 vCPU dá conta, desde que as consultas estejam indexadas.

Ou seja: o problema não é vazão. São quatro coisas específicas, e três delas eu encontrei medindo, não pensando.

Gargalo 1, a corrida no índice único

O findOrCreate procura por id. Se duas pessoas, ou dois aparelhos da mesma pessoa, regam a mesma prática no mesmo dia com ids diferentes, ele não acha, tenta inserir e bate no índice único (pratica_id, data_ref).

Cenário, 12 requisições simultâneasAntesDepois
Mesmo id (toque duplo, retry, fila subindo duas vezes)12 de 12 · 1 linha12 de 12 · 1 linha
Ids diferentes, mesma prática e mesmo dia1 de 12 · 11 erros 50012 de 12 · 1 linha

O banco ficava certo, com uma linha só. Mas onze pessoas recebiam erro por uma ação que deu certo. A correção é deixar o Postgres decidir, e ela tem um detalhe que economiza uma madrugada: violação de unicidade dentro de uma transação aborta a transação inteira, levando junto a anotação que ia ser gravada. ON CONFLICT não levanta violação, então a transação segue viva.

INSERT INTO registro (...) VALUES (...)
ON CONFLICT DO NOTHING          -- sem alvo: cobre a chave primária E o índice do dia
RETURNING *;
-- se não voltou linha, alguém chegou antes: leia a vencedora e devolva 200, não 500

Gargalo 2, o Argon2 no pico de login

O Argon2id está em 19 MiB e uns 250 ms por hash, o que é proposital: é o que segura ataque de GPU. O efeito colateral é que login é a rota mais cara do sistema. Numa máquina de 2 vCPU são cerca de 8 hashes por segundo.

Se 200 pessoas precisarem entrar às 6h, sem limite o Node aceita as 200 de uma vez: 200 × 19 MiB = 3,8 GB e a CPU travada. O processo morre por falta de memória, e aí ninguém entra, nem quem já estava logado.

O limitador resolve, mas a primeira versão dele não funcionou, e o motivo vale guardar:

// ERRADO: await cede o controle mesmo com promessa já resolvida.
// As 20 chamadas passam pela verificação antes de qualquer incremento.
await this._vaga();     // verifica rodando < limite
this.rodando++;         // só incrementa depois. Tarde demais.

// CERTO: o contador sobe no mesmo passo síncrono da verificação.
_vaga() { if (this.rodando < this.simultaneos) { this.rodando++; return Promise.resolve(); } ... }

Medido: com o limite em 4, a versão errada deixava 20 rodarem juntas. A corrigida segura em 4, e com 60 logins e espera curta, 16 passam e 44 recebem 503 com Retry-After, que é uma resposta honesta e que o app sabe tratar, em vez de o servidor cair.

Gargalo 3, o rate limit que se dissolve

Falha silenciosa

O @fastify/rate-limit guarda a contagem na memória do processo. Com três instâncias atrás de um balanceador, o limite de 10 logins por 15 minutos vira 30 na prática, e a proteção contra força bruta se dissolve sem nenhum erro aparecer em lugar nenhum. Assim que existir a segunda instância, o Redis passa de opcional a obrigatório.

O bloqueio de conta por tentativa falha continua funcionando, porque o contador dele mora no banco. É a razão de ele existir junto do rate limit, e não no lugar dele.

Gargalo 4, o pico que você mesma cria

O erro que parece certo: "o lembrete é às 6h, então mando todo mundo às 6h". O que acontece: 30 mil notificações no mesmo segundo, o serviço de push enfileira, e pior, 30 mil pessoas abrem o app no mesmo minuto. É negação de serviço feita em casa, com hora marcada.

A correção é um deslocamento determinístico por pessoa, derivado do hash do id. Determinístico importa: ela recebe sempre no mesmo horário, então continua sendo hábito e não loteria.

Sincronização em lote

Quem ficou 5 dias offline tem 15 itens na fila. Se cada item virar uma requisição, mil pessoas viram 15 mil requisições no mesmo minuto, cada uma pagando handshake, verificação de token e uma conexão do pool. Com POST /v1/sync, a mesma pessoa faz uma requisição, uma transação, uma conexão. O ganho não é de CPU, é de fila: a conexão fica presa por 40 ms em vez de por 15 idas e voltas.

Duas regras que fazem o lote não virar problema: teto de 200 itens, para a transação não segurar conexão por dez segundos; e item recusado volta identificado, para o app tirar da fila em vez de tentar para sempre.

Pool de conexões, a conta

pool.max por instância × número de instâncias precisa caber no max_connections do Postgres, com folga para migração e para você abrir um psql. Com max: 10 e 4 instâncias são 40 de 100. Confortável.

Acima de 8 instâncias, PgBouncer em modo transação. Aviso: nesse modo, prepared statements quebram, e o Sequelize os usa. É configuração, não é impossível, mas não é o dia de descobrir isso durante um incidente.

O que NÃO fazer agora

Adiar

Réplica de leitura. Só faz sentido quando a leitura estiver saturando a primária. Antes disso é uma fonte de bug de replicação atrasada, com a pessoa regando e a tela dizendo que não regou.

Adiar

Microserviços. Um app com sete tabelas e uma desenvolvedora não tem problema de acoplamento, tem problema de tempo. Dividir agora só multiplica o que você mantém.

Adiar

Cache de leitura. O que dá para cachear (trilhas, catálogo) é pequeno e raramente muda. O que é grande (diário) é por pessoa e cifrado. Ganho pequeno, invalidação complicada.

Web primeiro, loja depois

A decisão é começar pelo navegador, sem publicar nas lojas, até haver gente suficiente para justificar o esforço. É uma escolha defensável, e ela tem um preço específico que precisa estar visível antes de começar.

O que você ganha
  • Zero atrito. Um link abre o produto. Sem loja, sem instalar, sem revisão da Apple.
  • Você publica quando quiser. Corrigir um texto leva um deploy, não três dias de análise.
  • O design system já é CSS. A landing e o app compartilham os mesmos tokens sem conversão.
  • Link direto para o dia. Você manda o devocional de hoje por WhatsApp e ele abre na tela certa.
O que você paga
  • O lembrete no iPhone fica fraco. É o item mais grave, detalhado abaixo.
  • Sem biometria para destravar o diário.
  • Busca do diário limitada a filtro por tag e por referência.
  • Sem descoberta pela loja, então todo usuário vem de canal seu.

O problema do lembrete, que é o motor de retenção

Encare antes de decidir

No iPhone, notificação de site só funciona depois que a pessoa adiciona o site à tela de início. Não é uma configuração que você liga: depende de a pessoa abrir o menu de compartilhar e escolher "Adicionar à Tela de Início".

Traduzindo para o seu produto: a maior parte dos usuários de iPhone simplesmente não vai receber o lembrete diário, que é justamente o mecanismo que faz alguém voltar amanhã. No Android o cenário é melhor, mas ainda depende de instalar o PWA.

Três saídas, e elas se somam:

  1. Pedir a instalação na hora certa. Não na primeira visita. Depois da terceira rega, quando a pessoa já viu valor, com uma tela que explica em uma frase por que instalar, e mostra o gesto do iPhone com imagem.
  2. Lembrete por outro canal. E-mail funciona mal para hábito diário. WhatsApp funciona, e você já opera Evolution API, então a infraestrutura existe. Regras: só para quem pediu, com opção de sair em toda mensagem, e o texto do lembrete nunca carrega conteúdo do diário.
  3. Medir a diferença. Acompanhe retenção de 7 e de 30 dias separada por plataforma. Se o iPhone sem lembrete retiver muito abaixo, você tem o número que justifica publicar na loja, em vez de um palpite.

Autenticação: cookie na web, Bearer no app, uma API só

No app o token mora no Keychain, que só ele abre. Na web não existe equivalente, e guardar token em localStorage significa que qualquer XSS lê a sessão e a leva embora. Cookie httpOnly não é lido por JavaScript nenhum.

A troca: cookie é enviado pelo navegador automaticamente, o que abre a porta para CSRF. Um problema não substitui o outro, os dois precisam de resposta.

// login: o app se identifica, o navegador não precisa
if (req.headers['x-cliente'] !== 'app') {
  const csrf = app.gravarSessaoWeb(reply, tokens);  // grava 3 cookies
  return { csrf, usuario };                        // o token nunca chega ao JS
}
return { ...tokens, usuario };                      // app nativo recebe no corpo

A verificação de CSRF só se aplica a quem entrou por cookie e só em método que altera algo. O Bearer do app é imune por construção, porque o navegador não o envia sozinho. E a comparação usa timingSafeEqual, não ===.

Offline na web

O expo-sqlite na web está em alpha e exige WASM no Metro mais os cabeçalhos COOP e COEP para liberar SharedArrayBuffer. Esses cabeçalhos quebram embutidos de terceiros e complicam a hospedagem. Para o que a fila precisa, IndexedDB puro resolve sem cobrar nada disso, e é o que está em fila-offline.web.ts.

O que se perde: sem SQLite não há FTS5, então a busca por palavra dentro do diário não existe na web. O servidor também não pode buscar, porque o texto está cifrado. Sobram os filtros por tag, que funcionam pelo índice cego já no banco, e por referência bíblica, que está em claro. Isso precisa aparecer na interface, não ser descoberto pela pessoa.

O caminho de volta para a loja

A boa notícia é que quase nada precisa ser refeito, desde que estas três coisas sejam respeitadas desde já:

1

Diferença de plataforma vive em arquivo, não em if. seguro.web.ts ao lado de seguro.ts. O Metro escolhe sozinho e o resto do código não sabe da diferença.

2

A API já fala as duas línguas. Bearer e cookie convivem hoje. Publicar o app nativo não exige mudar uma rota.

3

Nada de API só de navegador. Se um componente usar window ou document direto, ele quebra no nativo. Isole no arquivo .web.

Quando decidir publicar, o que sobra é gerar as builds com EAS, preencher as fichas das lojas e passar pela revisão. A Apple costuma questionar app que é "só um site embrulhado", então a versão nativa precisa entregar o que a web não entrega: notificação confiável, biometria e a busca completa do diário. Convenientemente, essa é exatamente a lista de tudo que você abriu mão agora.

Usabilidade: o que não se negocia

Seis regras. Se uma tela quebra qualquer uma, ela não sobe, mesmo que esteja bonita.

No código
  • 44 px de alvo de toque, sempre. O botão pequeno tem 36 px de altura visual e por isso precisa de hitSlop.
  • Rótulo acessível em tudo que não tem texto. Botão só de ícone sem accessibilityLabel é um botão mudo no leitor de tela.
  • Estado nunca só na cor. Pedido respondido diz "Respondida em 28 de agosto", não só fica verde.
No teste
  • 360 px com fonte do sistema em 200%. É onde layout de devocional quebra, e onde parte do público realmente está.
  • Uma mão, polegar direito. A ação principal fica no terço inferior da tela.
  • Registro em menos de 15 segundos, do desbloqueio ao confirmado. Cronometre com cinco pessoas.

E a regra que vale mais que as seis: teste no sol. Abra o app na rua, ao meio-dia, num celular com brilho automático. É o teste que reprova mais paleta bonita do que qualquer ferramenta, e o público deste app faz devocional na varanda de manhã.
